推理的计算与数据搬运
将 MoE 模型映射到推理硬件：结构、流程与高效服务

混合专家（MoE）如今已广泛应用于前沿模型，它改变了服务结构以及有效推理的经济性。它所带来的不
只是参数数量的增加。它改变了每个 token 激活哪些张量、哪些内容必须保持彼此靠近、哪些传输需要强
大的本地带宽、哪些能够容忍较弱的网络链路，以及内存移动、存储和调度如何贡献于有效吞吐量。
最好的起点是把服务作为一个整体来看。推理运行在一个由编排层协调的集群内，例如 NVIDIA
Dynamo、Mooncake 或自定义调度器。这些编排层与 vLLM 或 SQlang 等推理服务器紧密协作，而这些
推理服务器也有自己的编排功能。本文不会详述如何使用编排软件，也不会说明你应该选择哪一种。本文
旨在概述这一过程，以及你可能使用的各种功能背后的原因。
用户（或其 agent）用一个请求（查询）开启一段对话，而在回答之后，对话还可以通过更多请求继续下
去。一次请求-回答称为一个“轮次”。在现代 AI 系统中，用户通常是在一个客户端应用（无论是图形界面
还是命令行形式）中运行，而 AI 返回的部分回答会被该应用截获，作为它要执行的指令，比如编辑你的代
码，或在某个 HR 问题上检索你公司的准则。
AI 系统也可以从自己的数据中心自行完成其中一些事情，例如它可以搜索网页。这些拦截到的工具操作结
果也会以请求的形式返回给 AI，从而产生更多轮次。服务器保存一份上下文（通常称为 KV cache，或简
称 cache），它是本次会话的提炼，使来自用户或工具的每个新请求都能被正确解释，以推动整体向前推
进。当用户针对长时间运行的任务启动一个 agent 时，每小时可能有数千个轮次。对话也可以暂停，并在
数小时甚至数天后恢复。
当请求到达推理服务器时，编排会把它放入一个队列，随后连同系统提示和对话先前轮次的任何上下文一
起送入输入填充工作器。查询随后被转换为新的上下文，追加到对话中。这份新的上下文状态然后被移到
解码工作器。解码反复读取累积的状态、生成答案 token，这些答案 token 也被追加到对话状态中。该过
程可能在工具、agent、用户以及后续的输入填充工作之间循环。运行在 GPU 上的模型工作器只是这个
Token Factory 的一部分；存储、网络和编排连接起它的各个流水级。
在工作器内部，从一开始就值得区分四种运行区间：
预填充，即把最初的一批新 token 一起处理。
中填充，其中延续请求被追加到现有的已缓存上下文。
解码注意力，其中上下文用于生成新生成 token 的基础内容。
解码专家，其中每个基础新 token 由从大量可能的专家集合中选出的一组专家进行细化。
这些模式对计算、内存和网络提出了不同要求。预填充与中填充密切相关，预填充就是先验上下文为零的
中填充。不过，预填充是一种常见的特例，对应经典“聊天机器人”式的一次性查询，并且可以比中填充
做略微不同的优化。预填充达到较高的算术强度（计算量与数据移动量之比），而且无需等待上下文被定位
和读取。中填充从用于先前状态的现有 KV cache 开始，并追加新的请求输入序列。它通常比预填充具有
更适中的算术强度，因为每个 token 对应的新 token 更少，而需要移动的现有数据更多。

解码注意力与解码专家工作通常算术强度较低，因为与先前上下文或专家权重相比，新 token 很少；在解
码状态下，这些权重是需要移动的数据。同时，在所有这些工作中，用于注意力和用于专家的张量无论
token 值如何都相同，因此让尽可能多可排队使用该张量的 token 共享对该张量的一次读取是有益的，甚
至包括来自其他用户无关请求的 token——这些请求只是恰好同时运行，并且网络连接足够紧密可以共
享。将这四种模式视为同一工作负载，会放弃 MoE 模型在不同强度和不同共享模式方面提供的许多结构优
势。
在本文档中，我们将分别处理这 4 个流水级，并有时假设它们是解耦的。聚合式（模型留在一台服务器
上，并随着请求在各流水级之间推进而重新配置）与解耦式（编排器可能在另一台已适当配置的机器上找
到空闲槽位）之间存在取舍。一般来说，我们会把各流水级视为解耦的，而聚合式是一种特例：当前一流
水级完成时，总是让当前节点可用。在更完整地介绍待完成的工作之后，结尾会有一节讨论这些取舍。
Transformer 模型是重复层组的深层堆叠。一个组可能包含一种层，也可能包含一个全注意力层以及若干
线性、局部、选择性或其他优化注意力层（这是混合层组）。在每一层内，注意力、共享变换、路由、选定
专家和重组按顺序发生。这些步骤提前已知并持续重复，使同一硬件资源能够在不同时刻服务于流程的不
同部分。
这些机器也可以被描述为同样简单的重复单元。节点是一组加速器，通常是机架中的一个托盘，每个加速
器将计算与本地快速内存配对。节点由 CPU 协调，并通过 NIC（网络接口控制器）连接到其他节点。节点
堆叠成机架。当需要非常大的张量时，机架可以作为一个纵向扩展域、多个较小的纵向扩展孤岛，或一组
流水级。数据中心网络随后将有界工作器连接到存储和编排，而不是参与每一项内部张量操作。
本文遵循这一脉络。它从全局服务和运行模式开始，然后将模型展开为宽层组切片，并将它们映射到加速
器节点和机架上。由此展开流水线并行、张量并行和专家并行；KV cache 内存施加的限制；批处理在预填
充、中填充和解码中的不同价值；以及调度在多机架 token 工厂中的作用。

1. 编排通过队列将请求送入工作器池
推理服务是一个集群：先前的请求和不可变状态在空闲时被存储起来，当新请求带入上下文或先前请求被
唤醒以继续时，它们被排队投递给专门的工作器。进入的队列还不是一个批次。每个请求携带提示
token、对可复用上下文的引用、服务目标，并且通常还带有已有的对话或 agent 状态。编排器可以把它
放入预填充、中填充或解码批次，而该请求可以在完成时独立地加入或离开该批次，从而把这份容量释放
给新的工作。当调度器知道哪些工作器拥有与请求上下文长度和服务目标相匹配的空位时，连续批处理的
效果最好。
预填充工作器从一大块新 token 中创建上下文。它们的输出是每个模型层的新 KV 状态，独立于创建它的
工作器存储。KV 状态沿着模型层移动：某一轮中第 K 层的输出会成为下一轮中第 K 层的输入。在流水线
化的服务器中，这自然形成了输出与输入分别来自不同 NIC 的“洪流式”传输。
中填充工作器扩展此前已处理的上下文。缓存的前缀可能包含系统提示、用户提示、记忆、更早的对话轮
次、agent 步骤或检索到的文档。大型根可能已被缓存，而增量输入可能远小于一个相当规模的未缓存请
求：一个 50 万 token 的上下文可能只接收几百或几千个新 token。
解码工作器消费已处理、已累积的上下文，并在每次传递中生成一个或少量 token（多 token 预测正变得
相当常见）。每个生成的 token 都会增加少量新状态。之后，当用户、工具或 agent 贡献另一块输入时，
同一上下文可以返回中填充工作器。使用工具的 agent 式工作会形成上下文扩展与生成的重复序列，而不
仅仅是一次预填充后接一次解码。
一个工作器可以占用一个节点、一个托盘或一个机架。服务通过运行许多有界工作器并在它们之间移动请
求和状态而变得大规模。取决于精度和工作状态需求，即使是数万亿参数的模型也能容纳在现代机架级系
统的聚合内存中。数据中心网络仍然必不可少，因为该工厂必须把许多这样的工作器连接到共享存储，并
持续让工作器配置匹配需求。KV 传输的大小可能达到数 GB，但它们可以在多条链路和目的地之间条带化
或洪流式分发；其移动时间仍可远低于一个长解码作业的寿命。

2. KV 状态以不可变数据块形式移动
在数据中心规模上，可复用的上下文变成了一个由不可变数据块组成的共享对象存储，而不是附属于某台
机器的文件。系统提示、项目上下文、先前的用户轮次、工具输出和生成的 token 可以分别位于不同的数
据块中。新的操作读取它所需的数据块并追加新的数据块；已有的数据块通常保持不变。这种只向前推进
的结构与因果 transformer 本身相一致。变更可以通过回溯并创建一个新分支来处理，而不是重写公共路
径。

这些数据块的持久来源是一个快速、并行、横向扩展的内存与存储池。它需要足够的聚合带宽和网络覆盖
范围，使得预填充、中填充和解码工作器可以依据适配性和可用性被选择，而不是因为某台机器拥有该上
下文的唯一副本。新近闲置的数据块可以先迁移到共享的网络附加 DRAM，包括节点 CPU 内存和专用内
存设备。随着该层被填满，分类器可以丢弃不太可能被复用的数据块，或将生命周期更长的状态提升到
SSD。底层的文本和引用通常比展开后的 KV 表示小几个数量级，因此如果分诊决定复用空间并丢弃了展开
的嵌入状态，可以从这份更小的文本重建 KV 数据块。AI 计算可能会有细微差异，因此虽然重建后的状态
可以预期是一个有效上下文，但不同服务对于丢弃和重建的随意程度，以及保留多少重要的不可变状态，
可能会采取不同的做法。
如果想更深入地了解这些数据块是如何管理的，推荐阅读 统一基数树缓存：面向混合模型前缀缓存的单树 -
LMSYS Org。它并非最终定论，但写得清晰，并且如果你想寻找更多资料，它会为你指向其他来源。
对于会增长到最大上下文的长时间运行 agent，状态也会频繁被压缩，因此一般来说，在一次压缩之后，
会有许多先前的数据块因为让位于新上下文而被废弃。压缩前上下文所占的空间很可能会被回收用于新的
工作。

加速器 HBM 是“热”工作层。它过于昂贵且受供应限制，不适合作为被动上下文存储的默认选择。活跃
的前缀和后缀应在使用前不久进入 HBM，并在工作器用完它们后迅速离开。CPU DRAM 是有用的暂存与
组装层，尤其是对于向外发送的状态：已完成的工作器可以把新生成的数据块移入 CPU 内存，同时存储系
统选择放置位置和冗余方式，之后由 NIC 将它们发送到共享池中。
对于传入数据，支持 RDMA 的系统可能允许网络将数据直接放入加速器内存，避免经由 CPU DRAM 的完
整拷贝。CPU 内存对于元数据、协调、部分组装、回退路径、副本以及向外发送的暂存仍然有用。当工作
器使用多个 GPU 时，传入的上下文可以直接并行地条带化到它们各自的目标内存中。

机架级的热数据块缓存也可能有用，无论是以内存/存储设备的形式实现，还是利用分配给分布式存储池的
CPU 内存。诸如系统提示这类非常常见的对象是天然的候选。这些缓存应保持为共享的横向扩展资源，而
不是把某个请求绑定到某台解码机器的私有状态。HBM 比 DDR 贵几倍，供应也更受限。HBM 的最佳用
途是用于当前正在创造收入的活动批次中的数据。

数据输入通常大于输出。中填充通常读取一个大的前缀并追加一个有意义的但更小的后缀。解码读取累积
的上下文，只追加一个或几个生成 token 的状态。读取会重复进行，写入通常只发生一次。系统设计应当
用各条数据通路的宽度直接体现这些差异。
3. 预填充、中填充和解码形成不同的运行模式
全局服务包含若干种计算区间。它们之间的差异比计算受限和内存受限这类笼统标签更有用，因为每一种
都有不同的复用机会，以及在硬件上不同的自然映射方式。
3.1 预填充
经典预填充从很少或没有可复用 KV 状态开始，处理一大块新 token。这些 token 共享权重加载，高效使
用矩阵运算，并产生足够多的被路由激活值，形成有用的共享专家批次。注意力与稠密变换可以达到很高
的算术强度，因此预填充通常主要受计算约束。较长的初始输入上下文可能提高内存流量，但这些很少达
到 100,000 token 的长度，而中填充通常会超过这个长度。

3.2 中填充
中填充把新 token 追加到长得多的缓存前缀之后。这个新块仍然可以提供数百或数千个激活值，用于共享
权重和专家的复用，把算术强度提升到每字节数据数千次运算。注意力还必须读取庞大的现有 KV 状态，
这可能达到数十 GB。因此它处于一种混合区间：比解码有更多的算术复用，但比相同新增 token 数量的初
始预填充有多得多的缓存状态流量。
3.3 解码注意力
解码每个查询仅以一个或几个 token 作为输入继续推进。每个查询都带着自己的 KV 状态，其长度与中填
充所处理的状态相近。预填充与中填充的区别在于缓存长度，而解码与中填充的区别在于输入序列长度。
这一到几个输入 token 使算术强度保持很低，这项工作显然由围绕 KV cache 的内存搬运所主导。
对于长上下文，注意力读取可能超过与模型权重相关的张量运算规模。因此，尽管大多数模型参数位于专
家之中，注意力仍是现代解码中最大的运算之一。Delta、top-k 或线性注意力算法层可以减轻负担，但周
期性使用带全注意力的层仍然是巨大的内存负载。每个查询都带来自己的上下文，因此对查询做批处理并
不会改变注意力的算术强度。
3.4 解码专家
专家并非解码阶段专属。模型在哪里运行，专家就在哪里运行，而它们除了一个 token 的嵌入之外不需要
任何上下文。查询的历史已经被压缩进呈现给专家的激活值中。这使得各种设计成为可能：在所有可用
GPU 之间共享专家，降低每 GPU 的内存占用并提高内存带宽与内存大小之比，即内存强度比。你可以把
GPU 读取其全部专家所需的间隔视为最佳情况下的交互性（每个用户看到的 token 速率），因此如果内存
带宽保持不变，而 GPU 负责的专家更少，交互性就可以更高。问题在于网络需求也会上升，而路由到专家
所需的 all-to-all 模式是一种很难处理的模式。
在注意力结束时（无论在预填充、中填充还是解码中），一次路由器计算（一个作用于未精炼 token 的小张
量）会为每个新 token 选择几个专家。选中同一专家的 token 可以共享张量权重加载，即使它们来自不同
请求，只要它们能及时被聚集在一起以利用同一次权重加载。实践中，所有层加起来可能有 15,000 个专
家，因此要利用这种巧合，需要有意的同步，比如等到一批中所有查询都完成注意力后再切换到把它们发
送去做专家工作，而这又可以通过让附近不同机器上的多个实例也同步到该调度来改善。如果你曾好奇为
什么 Nvidia 如此努力地把 72 个 GPU 紧密连接起来，这在很大程度上就是原因。在一个大型 Token
Factory 中，让这 72 台机器全部同步运行是可行的，从而把一层的专家最多分成 72 份。如果模型的一层
有 256 个专家，那么每个 GPU 在每层只处理 3 或 4 个，从而可以非常快速地完整轮转所有专家。同时也
带来大量的 all-to-all 流量。
如果你的专家都能放进 SRAM，就会发生一件有趣的事。你需要海量的加速器和一张巨型网络，才能把它
们全部收集并 all-to-all 回 GPU，但此时已几乎没有理由等待批次形成。每个专家只要有输入就可以运
行。每字节加载的能耗比从 HBM 加载好最多 100 倍，因此单个 token 运行时的效率可能相当于过去排队
100 个 token 时。作为这种 DAF（解耦注意力-FFN，其中专家就是 FFN）的回报，你可以让实例摆脱同

4. 通过 MoE 预填充层的数据流
经典预填充从注意力开始。一组新的查询 token 会关注可复用的前缀（如系统提示）以及新块中的较早位
置。注意力操作会为每个新 token 产生一个激活值，共享变换会将这些激活值准备好，供路由专家流水级
使用。
路由器会为每个 token 分配若干专家。如果模型选择八个路由专家，那么每个输入 token 会在一个可能包
含 256 个或更多专家的专家库中产生大约八条路由。按 token 顺序看，这些记录稀疏且交错：相邻 token
可以具有完全不同的目的地。然而，在整个输入块上，每个专家都可以累积一个简短的已分配 token 列
表。
工作器按专家标识符对路由记录进行排序或排队。所有分配给专家 037 的激活值组成一条消息流；分配给
专家 142 的激活值组成另一条消息流。随后，一次专家权重加载就可以服务该桶中的所有激活值。多个请
求可以汇入相同的桶，运行同一层的独立注意力实例可以在专家目的地合并它们的路由工作。将 token 顺
序转换为专家顺序是 MoE 预填充的核心效率来源之一。像 NVLink 这样的纵向扩展网络可以组织为内存
映射连接，因此向特定专家发送请求可以映射为将消息推入配置为硬件队列的特定内存映射位置。启停时
间非常少。专家可以通过等同于 RDMA CIQ 的机制监听，这同样利用硬件加速来交付消息流，无需复杂的
协议启停。消息内联的简单头部标识发送方和接收方。可以为从专家返回解码工作器的返回流建立类似的
连接。

===== PDF PAGE 10 / 33 =====
专家输出会被恢复为 token 顺序，进行加权、合并，并传递到下一层。与此同时，注意力会为追加的
token 创建新的 K 和 V 状态。在整个模型中，这些值形成一个不可变的 KV 后缀，用于解码下一个
token，并最终作为上下文中的下一个数据块存储起来，供对话的下一轮使用。
因此，预填充结合了两种权重复用形式。注意力和稠密变换会在许多 token 之间复用权重，而路由专家会
在其桶中收集到的 token 之间复用每个被选中的专家。随着激活流量、KV 流量和输出处理的增长相对于
张量计算占用更多时间，这些收益最终会趋于平坦。批处理可能延迟首个 token 时间，但单个包含数千个
新 token 的请求已经提供了可观的算术强度；预填充并不总是需要每批有大量请求才能高效运行。现代单
插槽 GPU 甚至可能在大模型上以约一秒完成小批次的预填充。

5. 通过 MoE 解码层的数据流
解码在每次前向传播中开始的新工作量要小得多。当前 token，或 MTP（多 token 预测）中的少量推测
token，是查询。注意力会读取先前的 KV 状态以及新 token 的 KV 条目。新条目会追加到结果中，并被追
加到 KV 状态中，供下一次前向传播使用。
对于 agent 上下文，先前的 KV 状态通常比那一个 token 所使用的注意力和专家权重构成更重的读取负
担。新的查询及其局部投影权重相对紧凑。注意力可以跨 KV 头、上下文范围、内存通道或加速器单元进
行划分，之后将部分结果归约为一个 token 激活值。该激活值足够小，可以低成本移动，尽管它会在下一
阶段触发大得多的本地张量运算。
激活值会经过共享变换和路由。路由器会从可用专家库中选择少量专家，只有这些专家的张量会针对当前
token 变为活跃。它们的输出会被加权、合并、投影，并继续向后传递。
在每一层，注意力会为新 token 创建并保留该层的 K/V 条目。随后激活值会前进到下一层的注意力，在那
里重复相同的序列。等到最终层生成下一个 token 时，每一层都已追加了其较小的 K/V 更新。在 token 被
流式发送到客户端或 agent 的同时，这些更新可以组装成一个新的不可变 KV 后缀。

===== PDF PAGE 11 / 33 =====
因此，该流程同时包含宽泛操作和稀疏操作。注意力会在私有查询状态上广泛读取。专家只激活模型总容
量的一小部分。硬件映射应同时支持两者，而不应迫使整个层使用同一种并行策略。

6. 中填充是一种独特的运行模式
中填充将一长段已缓存前缀与一块新 token 结合起来，为对话或 agent 工作中的另一轮做准备。追踪数据
显示，缓存输入比增量查询大许多倍，尽管增量查询通常从 50 到 5,000 个新输入 token 不等。已缓存的
系统提示、对话根、记忆、先前 agent 步骤和检索文档的存在，可以迅速将对话和 agent 上下文推高到百
万上限。AgentX 数据集显示，前沿专家会反复压缩上下文，以保持在百万 token 限制以下。
现代加速器通常可以利用由数百个 token 组成的块中可用的算术复用，因此困难的平衡往往在于大量 KV
读取与路由专家流量突发之间。这种突发与解码流水线的平滑节奏不匹配：一次中填充占用某个流水级的
时间可能远长于相邻流水级中的解码批次，导致这些流水级利用不足。
理想并行方式也可能不同。本文后面的示例发现，中填充配置使用与解码不同的流水线、张量和专家并行
设置。在正在运行解码流水线的中途重新配置 GPU 可能代价高昂或不切实际。因此，服务可能受益于专用
的中填充优化节点池。硬件可以与解码池相同，而加载的模型流水级、并行方式和批处理策略不同。

7. 模型是由重复层组构成的高堆叠
模型的参数数量量化了总的学习状态，但服务取决于该状态如何组织和使用。模型由层堆叠而成，而将这
些层归组为重复的架构单元正变得越来越有用。
在某些 MoE 模型中，一个层组等同于一层。在其他模型中，一个组包含一个全注意力层以及若干线性、
delta、top-k 或其他优化注意力层。通常最初的 1 到 3 层可能是稠密层，或以其他方式设计以获得干净的
起点。模型的其余部分通常会重复一种反复出现的组模式。
一张宽而浅的可丽饼是层组的一种有用表示。宽阔的表面为注意力、共享变换、路由、专家容量和残差流
提供空间。其浅薄的厚度表明该组只是一个高得多的重复模型中的一个切片。它也呼应了加速器的物理形
态：一层非常薄的活动层铺展在宽大的封装上。可丽饼是一种有用的直觉，用于将宽泛的算法流映射到宽
大的硬件表面。
重复结构简化了功能规划。为一个组创建的映射可以复用于下一个组。对应的内存区域可以存放下一组的
权重。相同的计算和通信计划可以重复执行。一致性不仅对运行时效率重要，对编译器、内核和运维工具
也很重要。

8. 并行应划分模型中的窄数据流
并行并不是一个单一决策。流水线并行、张量并行和专家并行划分模型的不同维度，并应根据不同的通信
模式来评判。
流水线并行沿层堆叠分布
层结构立刻让人想到流水线化。层与层之间传递的激活值很紧凑——通常是一个嵌入后的 token、一个小
的多 token 预测块，或对先前混合组结果的简短摘要——而层内部使用的权重和 KV 状态要大得多。因
此，一个流水级可以拥有一个或多个完整的层组，并把相对较小的激活值传给下一个流水级，而无需过强
的网络。
流水线并行干净地划分模型权重，并将热点层内通信保持在本地。其主要缺点是多批次占用：完全活跃的
流水线在每个流水级中都有不同的查询或批次。因此，每个流水级都为所有活跃流保存其那份 KV 状态，
而随着上下文增长，内存收益最终不再提升。
张量并行应放在单个操作本身很宽的地方
注意力可能需要将权重和 KV 状态划分到多个加速器上。可以划分 KV 头、上下文范围或另一个线性维度，
使每个加速器先处理其份额，然后对 token 结果进行紧凑归约。张量并行也可用于异常大的稠密变换。
张量并行（TP）不应自动扩展到该层的每个张量。对于大范围注意力操作而言合理的集合通信，其成本可
能超过一个小型专家张量的计算量。

===== PDF PAGE 15 / 33 =====
专家并行沿独立专家张量展开
大部分 MoE 参数内存可能驻留在专家中。专家本身不保留查询历史；上下文随激活值到达。因此，专家库
可以广泛分布在一个对等集合中，并由多个工作器实例共享。
宽专家并行很有用，因为专家彼此独立且数量众多。路由器将紧凑激活值发送到选定目的地，这些目的地
返回变换后的激活值。即使流水级变得更小，专家并行宽度仍可保持很大，从而可以独立选择交换机基数
和本地内存放置。
一般规则很直接：对垂直层序列使用流水线并行，对大型不可分割操作使用张量并行，对无上下文的被路
由专家库使用专家并行。当流水级的可用快速内存安全超过其本地权重、活跃批次状态和工作缓冲区时，
该流水级就能舒适地容纳在一个纵向扩展域内：
M_{free,node}>\frac{W}{P}+M_{batch}+M_{working}

现代 GPU 节点通常以数倍超过该阈值。当它们这样做时，苛刻的带宽、功耗和延迟要求可以保留在一个节
点内部，而更精简的流水线激活值和 KV 移动则使用横向扩展链路。快速内存的其余部分可能没有产生任
何收益。闲置在内存中的数据是成本，被移动去处理的数据是收入。

9. 逻辑加速器节点
将逻辑节点理解为按环排列的对等集合，比理解为字面电路板布局更容易。该环包含大约十六个加速器。
每个加速器将计算区域与本地快速内存配对。这些单元通过强纵向扩展互连结构连接。CPU 协调工作负载
与内存管理，而 NIC 将节点连接到机架和数据中心资源。
环只是一种可视化，用来显示加速器作为对等方地位平等。我并不是暗示节点内部网络应该是环。它可以
是中心辐射、轨、全互联、环面、超立方……随你喜欢，只要它能以低延迟和低每比特能耗处理机架中包
含的最高数据流。为简单起见，我只是把它画成环。
这种表示避免过早锁定封装放置、板级布线或交换机实现。实际机器可能使用一个中央交换机、多个交换
机、直接链路或分层互连结构。逻辑要求是一个有界对等集合，并具有可预测的快速本地通信。
加速器设计可能各不相同。一种版本可能使用大量 SRAM 的存内计算单元。另一种可能使用混合键合
DRAM，或在 BEOL 处理期间置于顶部的 IGZO 存储单元。还有一种可能使用混合键合的高带宽真正 3D
内存。内存容量和带宽可以变化，而这种逻辑模型仍然有用。
节点可能小于一个机架，例如我们看到的有 8 个 GPU 的 SGX 节点；纵向扩展系统也可能横跨整个机架，
例如 NVL72。无论哪种情况，逻辑符号都仍然有效。如果纵向扩展已经覆盖整个机架，则单独的机架骨干
层级消失，下一个边界直接是横向扩展网络。

10. 节点堆叠成机架
当环被倾斜为宽而浅的硬件可丽饼时，它会变得更具表现力。多个单元可以在机架中垂直堆叠，如同模型
层组沿模型深度堆叠。
这种重复形式使模型到硬件的关系更容易看出。一个层组可丽饼可以放置在一个硬件可丽饼上。如果内存
允许，多个层组可以占用一个节点。如果注意力或专家容量需要，一个层组可以跨越多个紧密连接的节
点。映射可以扩展或收缩，而无需改变基本可视词汇。
机架可以通过几种方式组织：
一个覆盖整个机架的纵向扩展域；
由机架骨干连接的多个节点级孤岛；
分布在这些孤岛之间的流水级；
每个流水级内广泛的专家放置；
或者流水级本地纵向扩展与共享横向扩展链路的混合。
因此，机架骨干是一个可选的中间层级。一些系统将纵向扩展互连结构扩展到整个机架，不需要单独的节
点连接器。另一些系统使用强本地节点互连结构和独立的机架顶部或共享轨网络。在机架之上，横向扩展
网络连接存储、预填充池、解码池和其他机架。
重复的机架单元还有助于区分两种规模。模型可以容纳在一个有界机架工作器内，而工厂通过增加许多工
作器来扩展规模。第一个问题是功能放置。第二个是工作器编排。

11. 一个层组随时间复用节点
层组不需要算法中的每个操作同时以峰值强度运行。其操作形成一个重复序列，在解码周期内复用同一硬
件完成不同工作。
同一批物理加速器可以在每一步以不同方式参与。计算注意力的执行单元稍后可以执行一个或多个专家。
用于流式传输 KV 状态的内存通道稍后可以为专家权重提供数据。随着 token 推进，缓冲区和本地链路会
被复用。
这种分时复用对高效设计至关重要。静态图可能使机器看起来未被充分利用，因为并非每个模块都同时活
跃。实际上，硬件正在服务于一系列不同操作，目标是让该序列以很少的设置或同步开销持续运行。
宽层组可丽饼与加速器对等集合是互补的。可丽饼展示算法流程；环展示其下可复用的物理资源。映射是
将流程的每个流水级与环的合适子集对齐的行为。

12. 将吞吐边界设在流量最小处
一旦模型和机器被绘制为相互连接的流程，放置规则就变得清晰：频繁、对延迟敏感的通信应保留在最强
的本地互连结构内，而较弱的链路应承载紧凑或可摊销的传输。
         Figure 17. The general flow of operation of an MoE pipeline stage (animated).
注意力分区可能每层交换部分结果。专家路由将激活值发送到选定的专家并返回其输出。这种流量按字节
数并不总是最大，但它频繁、突发且对同步敏感。只要可行，它应属于所选的纵向扩展域内部。
在层或层组之间传递的激活值要小得多。因此，流水线边界可以跨越较弱的链路，而无需移动该层的完整
内部工作集。KV 数据块更大，但它们在工器边界移动，并在许多生成的 token 上摊销。它们的路径可以
使用条带化或洪流式横向扩展网络和共享存储，而不必消耗最内层张量互连结构。
路由器到专家的边界通常是中等吞吐的全互联，承载紧凑激活值。其难点通常来自端点数量、同步和路由
效率，而不是原始字节量。将其保持在节点或机架的纵向扩展域内，可同时限制延迟和运维复杂性。

===== PDF PAGE 19 / 33 =====
这种层级结构比每条链路都同样强大的机器更容易、更便宜地构建。纵向扩展路径包围每一层内交换嵌入
和部分结果的操作。横向扩展链路承载流水线激活值、KV 移动、调度流量以及有界工作器之间的流量。
这些层级也有不同的延迟要求。如果吞吐足够，层组之间的流水线传输可能几乎注意不到几微秒。相比之
下，当专家加载与乘法只花费几微秒时，每个路由跳增加 100 ns 就很关键。因此，最近的链路应与加速器
互连结构紧密集成，而较不频繁的传输可以容忍横向扩展网络。
13. 在可行处按层组进行流水线化
层组是流水线放置的自然首选单元。在经典 MoE 模型中，该组重复一种层。在较新的结构中，它可能包含
一个全注意力层，后接若干优化或局部化注意力层。
将一个组保持在一起可以保留内部依赖关系，并使一个放置和编译计划在各流水级间重复。统一计划降低
工具链成本并简化部署。当每个流水级运行相同的重复结构时，内核、内存布局、通信调度、监控和故障
恢复都会变得更容易。
仍然可以在一个组的中间切分流水线，尽管由此得到的放置方案会更复杂。如果各层之间没有特殊的跨层
依赖，紧凑的激活边界仍然是一条低流量的链路，适合走网络。一个流水级可以包含若干个完整的组、一
个组，或一个大组的一部分，具体取决于显存和吞吐需求。
指导原则并不是绝对禁止切分组。而是优先采用规则的边界，并理解非均匀切分在什么情况下值得。工具
链与运维的简便性，可能与理论放置上的微小收益同样重要。

14. 流水线深度止于 KV cache 交叉点
流水线并行可以干净地划分模型权重。如果一个模型的权重占用为 (W)，并使用 (P) 个流水级，则每个流水
级的理想权重占用趋近于 (W/P)。

===== PDF PAGE 20 / 33 =====
KV cache 的需求表现则不同。整条流水线会一直处于占用状态，因为每个流水级都在运行不同的查询或批
次。在八级流水线中，每个流水级承担八条活跃流各自逐层 KV 值的八分之一。每级层数的减少被并发流
数量所抵消，因此流水级在活跃 KV 需求上并不能获得与权重相同的 (1/P) 缩减。
一个实用的流水级显存估算式为：
M_{stage}\approx \frac{W}{P}+M_{KV,stage}+M_{working}+M_{slack}

一旦每个流水级的权重降到与 KV 和工作状态显存同一量级，继续加深流水线带来的容量收益就很小，反
而增加协调开销和时延。
这个交叉点在很大程度上取决于模型设计。经典的全注意力方案在所有层上每个 token 可能需要数百 KB
的 KV 状态。类 MLA 的设计通常处于数十 KB 量级，而近期以线性注意力、循环注意力或局部注意力为主
的混合层组还可以更低。对于某些新的混合架构，每 token 约 25 kB 的工作平均值可能是合理的；对于一
个经过验证的压缩注意力设计，每 token 约 70 kB 是一个保守的参考值。
作为粗略的设计目标，取每 token 70 kB、分配给单个流水级的聚合活跃上下文 200 万 token。这大约是
140 GB 的 KV 状态。双缓冲允许一个工作集在迁移的同时另一个继续运行，从而把 KV 预算提高到接近
280 GB。再加上模型权重、激活、瞬态缓冲区、路由表、碎片和运行余量，约 400–500 GB 本地高速内存
的流水级目标就成为 2027 年一个有意义的基准。
其他设计可以通过流式传输、压缩、部分驻留或额外的存储层级来降低需求。这个估算并不是普适的硬性
要求；它是一条标准，一个实用的前沿系统应当能够在不需要英雄式假设的情况下满足它。
如果多个加速器插槽共享纵向扩展互联，流水级可以把这些显存分布到它们之上。大型 MoE 中超过 95%
的权重显存位于路由专家中，而这些专家可以自然地在插槽之间划分。KV 状态可以按头、上下文或注意力
实例进行分区，由此产生的集合通信可以匹配到同一套本地互联上。

15. 预填充和中填充将稀疏路由变为稠密专家批次
预填充和中填充具有很强的批处理机会，因为许多输入序列 token 在专家执行开始之前就完成了注意力计
算。路由器可以为所有 token 打分，为每个 token 输出若干个目的地，然后按专家对路由记录排序。
一个实用的输入块可以包含足够多的分配，使得基本上每个专家都能收到工作。如果 128 个新 token 各自
选择八个专家，路由器就会在一个 256 专家的专家库中产生 1,024 条分配。对每个 token 而言路由仍然是
稀疏的；排序改变了执行顺序，使专家 e000 处理完分配给它的所有 token，然后是 e001，依此类推。每
个专家只加载一次，并针对其紧凑的 token 列表复用，而不是按 token 顺序被反复加载。
对于一个拥有 (W) 个权重的专家、权重流量 (B_W)、每个路由 token 的激活流量 (B_A)、输出流量 (B_O)
以及 (n) 个被分配的 token，一个粗略的算术强度表达式为：
AI_{expert}\approx \frac{2nW}{B_{W}+nB_{A}+B_{O}}

当权重流量占主导时，增大 (n) 会迅速提升复用率。最终激活、输出和路由流量变得重要，收益随之趋于平
缓。

排序并非没有代价。必须构建路由记录、计数、置换、发送到专家目的地，再恢复为 token 顺序。专家容
量限制可能导致溢出或改路由。即便如此，预填充和中填充一开始就有足够多的 token，因此这一优化通
常是有意义的。
这正是它与解码的关键区别。专家是完全相同的；变化的是工作器执行这些专家时有多少可用的路由激
活。

16. 解码从批处理中获益较少
解码阶段的专家之所以有共享潜力，是因为专家权重与上下文无关。实际的限制在于共享概率。一个模型
在每一层中可能包含数百个路由专家，在整个模型中则有数千个层-专家。每次查询在每一轮中只贡献一个
新 token，并且只选择少量目的地。在小批量下，可用的路由 token 很少，大多数活跃专家只从一个
token 那里收到工作。会有一些共享发生，但它随着该轮中 token 数量的增加而逐渐增长。
当上下文长度达到 100,000 token 甚至更多时，批量为 1 并不是一个微不足道的工作负载。注意力扫描本
身就已经占用了大量内存带宽。最优批量并不一定是 1——软件启动、内存分配、路由和硬件利用率仍然重
要——但它可能更接近 1 或 5，而不是面向吞吐的服务所采用的大批量。

这在经济上很重要。交互式 token 可能比批量延迟 token 更有价值。为了获得百分之几的吞吐提升而成倍
增加时延，可能是一笔糟糕的交易。硬件和软件应当消除阻碍有用的小批量运行的障碍，而不是把大批量
当作效率的前提条件。

17. 调度让解耦发挥价值
解耦只有到云规模、作为一个统计系统时才最有效。一个大的资源池可以包含配置为长预填充、短预填
充、长上下文解码、短上下文解码或其他有用类别的工作器。编排器把每个作业分配给一个合适的可用工
作器，并通过共享存储搬运所需的 KV 数据块。
一旦前缀大小、新 token 数量和工作器配置已知，预填充和中填充工作就是可预测的。解码则是随机的，
因为输出长度不确定。资源池之间的存储把可预测的生产与不规则的消费解耦开来。一个已完成的预填充
和中填充工作的就绪缓冲区，可以在各个查询于不同时间完成的同时，持续为解码工作器提供输入。
调度器应当观察客户工作负载和时段模式，预判已知的负载爬升，并在混合比例变化时重新配置工作器。
重新配置可能意味着加载不同的模型流水级、改变流水线基数、重新分配专家容量，或在预填充、中填充
和解码之间移动一个机架。
规模至关重要。在小型固定基准测试中，一个预填充流水级可能直接连接到一个解码流水级。慢速流水级
会使其他流水级的容量闲置。在大规模资源池中，工作器独立完成和启动，因此无需有任何工作器被闲
置。
因此，高交互性和高利用率并非天生对立。只要调度器拥有足够的工作器、足够的存储带宽、对工作的足
够可见性，以及足够快的响应时间来适应当下，它就可以在保持批量很小的同时让机器保持忙碌。

18. 反馈会把微小失衡变成振荡
紧耦合的系统会放大普通的波动。假设输入填充的准入直接由解码查询的退役来把关。一个长时间运行的
解码查询延迟了退役。输入填充的准入下降。解码随后排空其就绪队列并变得供给不足。于是准入被激进
地打开，产生一批输入填充作业和新的拥塞浪潮。
这是一个延迟反馈回路。控制信号在系统状态已经改变之后才到达。大批量恢复会通过增加 KV 显存压力
和响应时延使回路更糟。整个工厂在满与空之间交替，而不是在某个稳定点附近运行。
没有哪一种调度器策略能解决这个问题。几种常见的控制技术会有帮助：
在各级之间使用就绪工作缓冲区；
根据平滑后的积压和预测的服务速率来调节准入，而不是依据单个请求的退役；
把快速的本地控制与较慢的容量控制分开；
对工作器重新配置施加迟滞；
为短的交互式工作预留容量；
并且不要让批量大小的变化速度快过系统观察其效果的速度。
同样的原则可以跨越多个时间尺度。微秒级的工作器调度、毫秒级的 token 流动、秒级的缓冲区、分钟级
的工作器重新配置，以及小时级的需求规划，不应当全都对同一个噪声信号作出响应。

19. 聚合式与解耦的对比
既然我们已经详尽描述了解耦推理（disaggregated inference），那么是否还有理由支持聚合式方案？在
某种程度上，有。显然，由于对话可能暂停数分钟甚至数小时，把整个对话绑定在一个系统上并不合理。
一个轮次结束后几秒内，那块 HBM 就可以被更好地利用，而现代横向扩展网络能在不到一秒内把数 GB 的
KV cache 迁移到并行存储系统中更便宜的位置，该系统可以对 DRAM 和 SSD 分层。
然而，在一个轮次内，我们是否需要安排不止一个位置来完成工作？拥有太多不同的服务器设计成本高
昂，会增加运营成本以及设计工作。如果只有一种设计，并且它以中填充场景为中心，会怎样？一个请求
可以被调度到那个空闲工作器，并在预填充、中填充和解码期间留在那里。它需要拥有足够的计算能力用
于预填充和中填充，以及足够的内存带宽用于解码。总会存在一些计算或内存传输方面的闲置容量，具体
取决于模型正在运行哪个流水级，但我们已经容忍 GPU 上较低的 MFU。我们试图用巧妙的内核来克服这
一点，但在实践中，集群一直带着闲置功能运行。
复杂的编排会导致一些闲置。如果一个轮次在单个聚合式工作器上运行，其中一些闲置就可以避免。预填
充/中填充交接给解码时没有调度间隙。宽并行专家集合的一份副本可以自然共享。把上下文从填充移动到
解码没有网络开销。编排器仍会查看请求的形态——缓存大小、输入序列长度、模型类型、客户交互性水
平——并做出一个决定：哪个可用工作器应处理该轮次的所有流水级。然后它不再干预，直到停止 token
出现，该轮次交付给用户并缓存到快速并行文件系统。这个工作器在处理该轮次的所有流水级时，使用适
配给定请求形态的内核和数据流。
聚合式工作器有其吸引力和拥护者。
所有系统在现实使用中总会闲置加速器的某些能力。在解耦系统中，可以有两种（或更多）类型的机器，
其投资集中在实际使用的计算、内存和网络上，可以说是对该投资的最佳利用。预填充机器可能投资于计
算，而解码机器可能投资于内存。如果工作器是聚合式的，那么一台机器将用于所有阶段，因此它需要投
资于最强的计算和最强的内存吞吐量。也许还需要强大的网络。如果它不是全能型佼佼者，就会被较弱环
节拖累，整体上“平平无奇”。所以，聚合式有优势，但在提供最佳全能性能方面也无处藏拙。如果你能打
造出那种神奇的全能明星，那么把一个轮次整体聚合在一个工作器中可能是最好的。
20. 内存带宽与内存容量是不同的目标
人们常把内存当作两个需要最大化的独立标量来讨论。在实践中，容量和带宽彼此权衡，它们的经济价值
必须一起考虑。
数据在流动时创造收入；在闲置时产生成本。具有极高内存吞吐量的加速器能以较低带宽内存无法匹敌的
速率生成 token，即使较低带宽配置拥有更大容量。容量在活跃权重、KV 状态、激活值和运行余量都能干
净容纳之前是有价值的。超过这一点后，额外的本地容量可能增加成本，却不会增加收入。
容量曲线并非垂直悬崖。在有用极限以下，增加加速器会同时提供更多内存和更多带宽。当其他限制出现
时，这些优势就结束了：最大纵向扩展宽度、不佳的模型切分、延迟占主导、额外同步或网络争用。
安全容量的设计点必须位于这些限制之上。它包括为现实上下文分布、双缓冲、碎片、故障和瞬时峰值留
出的余量。收入-容量曲线在该点之前陡峭上升，随后平滑过渡，然后达到主要由带宽和计算决定的更平坦
上限。如果过剩容量变成沉没成本，而运营方试图用吞吐量高但价值低的大而慢批次来证明其合理性，收
入甚至可能下降。

加速器 HBM 过于昂贵，不适合保存没有立即用途的闲置数据。已完成的 KV 数据块应移入 CPU DRAM
进行外发暂存，然后进入横向扩展存储。频繁复用的公共数据块可以继续复制保存在共享 CPU 内存或附近
的缓存设备中。只有活跃工作集才能负担得起最昂贵的内存。
高容量内存的高堆叠可能在功耗、信号质量、封装和频率方面带来成本。一个容量刚好足够且带宽卓越的
设计，可能比一个以闲置过剩来最大化每加速器容量的设计，以更高利润率服务交互式推理。

21. 一种实用的映射方法
前面各节可以浓缩为一种可重复的方法，用于把模型映射到机器上。
分离运行区间。 独立测量预填充、中填充、解码注意力和解码专家。每一类还可以按上下文长度或工作负
载类别进一步拆分——例如 agent、编码、媒体或内容创作。这些会成为预置配置，编排器可以在生产环
境中混合使用。
描述重复的层组。 识别完整注意力和优化注意力、共享变换、路由专家以及任何跨层依赖。
衡量活跃状态，而不只是总参数。 分离流水级权重、活跃专家、实时激活值、KV 状态和瞬态缓冲区。
为每个操作选择自然的并行维度。 对层堆叠进行流水线化，对宽大的不可分割工作进行张量并行化，并广
泛分布独立专家。
先映射最宽的操作。 长上下文注意力通常决定内存条带化和最小有用的纵向扩展参与范围。

===== PDF PAGE 27 / 33 =====
把专家权重放在规则的本地目的地。 让路由在已知对等位置之间选择，而不是为每个 token 创建全局事
件。大型模型可能包含约 15,000 个层专家，每个层专家都可以根据其层内其他专家以及预期路由分布来放
置。目标是均匀使用内存容量和带宽。
让重复的高吞吐量协作留在最强互连结构中。 让更稀薄的激活值和已摊销的 KV 移动跨越较弱边界。同时
尊重延迟和功耗悬崖以及吞吐量悬崖。
在 KV 内存交叉点停止增加流水线深度。 一旦模型和目标上下文以安全余量容纳，额外流水级带来的内存
收益很小，却会增加流水级转换延迟。
以不同方式使用输入填充和解码。 将预填充和中填充路由排序为专家批次；保持小批量解码的交互性。
与工作器一起设计存储和调度。 KV 移动、准入控制、就绪缓冲区和工作器重配置决定物理映射是否能产
生稳定吞吐量。短批次和连续批次更新让编排器可以替换单个请求，而无需等待整个批次退役。
该方法不会选择一种通用拓扑。它让权衡变得可见。一个对等集合可以是一个封装、一块板卡，或一个机
架级纵向扩展域。一个层组堆叠结构可以映射到一个节点或多个节点。重要之处在于，通信层级遵循模型
的实际流动。

22. 下一个视角是时间
到目前为止，这些图描述的是结构和流动。下一步是把时间叠加到它们之上。
交互式解码有紧张的端到端预算。一层的执行通常需要落在约 50 微秒到 1 毫秒之内，在典型的 60 层模型
上，这对应约每秒生成 15 到 300 个 token。每一层包含若干个顺序阶段，因此单个算术操作和交接处于数
十微秒、微秒，有时是零点几微秒的量级。
在那个尺度上，张量算术只是结果的一部分。内核启动、排队、同步、内存设置、路由、归约和链路延迟
都必须相对于它们所支持的操作保持很小。如果一个专家乘法只花费零点几微秒，而分发和数据移动各花
费数微秒，那么它的价值就会被稀释。

===== PDF PAGE 28 / 33 =====
时间视角也让网络层级更清晰。一条高带宽路径如果建立延迟太大，仍可能不合适。对于亚微秒级交接，
一个小的本地缓冲区可能比一个大的远端内存层级更有价值。一个会造成毫秒级波动的调度器，可能压倒
工作器内部精心的微秒级工程。
该工厂跨越多个控制时间尺度：
本地算术和链路交接在零点几微秒到微秒量级；
层执行在约 50 微秒到 1 毫秒；
token 生成在毫秒量级；
就绪缓冲区和准入控制在约 0.1 到 10 秒；
编排器进行工作器重配置在数秒到数分钟；
快速并行文件系统中的 KV 数据块保留和生命周期在数分钟到数天；
以及客户需求规划在数小时到数天。
这些循环应分别设计并谨慎衔接。快速控制不应追逐缓慢的需求噪声，慢速控制也不应对每一次瞬态队列
波动做出反应。

22.3 快速内存需求
第三张图显示每个 GPU 的峰值 HBM 占用。它不包含在 KV 状态进出工作器时所用的额外缓冲区，这些缓
冲区可能为每个 GPU 增加数 GB。在对话轮次或 agent 轮次之间，不活跃的 KV 数据块可以并行传输到网
络附加的 DDR，包括节点 CPU 所挂载的 DRAM。那类内存更便宜、更易获得，受 HBM 供应链的约束也
更小。
预测出的前沿曲线聚集在可行内存区间的低端附近。对于预填充和中填充，向下的台阶来自增加流水并行
以及提高张量并行或数据并行，包括数据并行的环形批处理实例。解码则首先通过张量并行或数据并行降
低每 GPU 的驻留量，之后才使用流水并行。
即使考虑到实际所需的 KV 传输缓冲区，大多数前沿配置每 GPU 仍低于约 80 GB。这支持了此前的结论：
只要更广泛的存储与编排系统能及时迁移闲置状态，带宽可能比在每个加速器上最大化 HBM 容量更有价
值。

22.4 网络峰值与纵向扩展边界
第四张图显示每个 GPU 的预测峰值网络流量。预填充和中填充因专家并行而密集使用网络，因为同一时刻

结语视角
推理分析中有用的单位并不只是总参数量，而是模型的活跃数据流与机器的内存、通信和时序层级相结合
的整体。
MoE 提供了结构。层组重复出现。专家数量众多但单个可控。注意力范围广泛，并日益受 KV 状态塑造。
操作按顺序执行，可以复用硬件。流水并行、张量并行和专家并行各自都可以沿着最自然的维度展开。预
填充和中填充可以把路由整理成高效的专家批次，而解码则可以保持短批量和高交互性。
以这种方式把握问题并不会消除它的规模。它让这种规模更容易被划分。模型、工作器、机架、存储系统
和调度器成为一个连贯设计的组成部分，可以被测量、说明和改进。
